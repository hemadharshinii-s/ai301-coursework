# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Plan fidelity (silent drift) | Compare the changed files and hunks in `git diff main...HEAD` against the planned scope and explicit `## Deviations` in `plan.md`. Compare each substantive claim in `pr_draft.md` against the actual diff and the linked issue's stated goal. | Every substantive change is within the plan or an explicitly documented deviation, and the PR description accurately represents what the diff does. An honestly disclosed omission or limitation passes if the remaining implementation is within the agreed scope and no claim falsely implies the omitted work is complete. | required |
| Test evidence (not tested) | Read `test_evidence.md` and compare its commands, outcomes, and observed behavior with the test plan in `plan.md`. Check that required repository checks from `.github/PULL_REQUEST_TEMPLATE.md` or `docs/CONTRIBUTING.md` have evidence of being run. For a bug fix, compare the documented before/after reproduction evidence. | Evidence identifies observable commands and results relevant to the planned change, demonstrates the intended fix or behavior, and records the applicable repository checks. A failed or unavailable check must be disclosed accurately; it does not pass if required behavior remains unverified or a claimed success has no supporting result. | required |
| Diff quality (unreviewable) | Inspect the changed-file list and hunks from `git diff main...HEAD` against the plan and issue. Look for unrelated changes, generated output, temporary files, debugging debris, accidental formatting churn, and unrelated test suppressions. | The diff is focused on the planned change and necessary tests or documentation. No unrelated or accidental changes obscure review of the fix. Necessary supporting changes are acceptable when their purpose is clear and they fit the plan or documented deviations. | required |
| Standards and communication (standards wall) | Compare `pr_draft.md` with `.github/PULL_REQUEST_TEMPLATE.md` and the relevant asks in `docs/CONTRIBUTING.md`. Check the title, issue reference, summary, changes, testing, screenshots/demo or justified N/A, reviewer notes, and required AI-use disclosure. Compare the description with the diff and test evidence. | The draft addresses every applicable template section, references the correct issue, describes the actual changes and tests truthfully, and includes required disclosures. A section may state N/A with a valid reason when it does not apply; do not require screenshots or features that the change does not need. | required |
| Issue alignment | Compare the linked issue thread's requested outcome and acceptance criteria with `plan.md`, the actual diff, test evidence, and PR description. | The change addresses the issue's intended problem, or clearly identifies a justified, bounded partial outcome without claiming the entire issue is resolved. No material contradiction with the issue's requirements remains undisclosed. | required |
| Review readiness | Read the plan, diff, test evidence, and PR draft together, focusing on whether a reviewer can verify the stated behavior and understand any limitations from the provided evidence. | A reviewer can identify what changed, why it changed, how it was checked, and any material limitation without relying on unsupported claims. Brevity is acceptable; missing evidence or a material ambiguity that prevents verification is not. | preferred |

## Verdict rule

Grade every listed check as `pass`, `fail`, or `unclear`, and provide one evidence line for each grade. Accept only when every `required` check passes. A `fail` or `unclear` on any required check means `reject`; an `unclear` grade counts as failing because the relevant claim is not verifiable. Preferred checks provide useful feedback but never change the verdict. Do not reject a package solely because it honestly discloses a bounded omission or limitation: judge whether the remaining change meets the issue and plan's stated scope, whether the disclosure is accurate, and whether required behavior is verifiably tested. Never invent missing evidence or change a check's pass condition during a run.
